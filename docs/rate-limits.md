# Rate limiting

Limits are per account and per endpoint (operation name such as `Followers`), in 15-minute windows. Each account's limiter is seeded with caps measured from x.com's `x-rate-limit-limit` header:

| Endpoint | Seed (requests / 15 min / account) |
|----------|------------------------------------|
| `UserByScreenName` | 150 |
| `Followers` | 187 |
| `Following` | 187 |
| `Retweeters` | 500 |
| `UserTweets` | 50 |
| `SearchTimeline` | 187 |
| `HomeLatestTimeline` | 500 |
| `DeviceFollow` | 180 |

The table is exported as `EndpointLimits()`, which returns a copy — mutating the result changes nothing. Only measured operations are listed; `RateLimitHeadroom` (2) exports the exhaustion margin the header authority applies, so a consumer can compute an account's effective budget without duplicating either constant.

Endpoints without a seed use `ClientConfig.RateLimit` (default 50 per 15 minutes). On every response from a pool request, an account-pinned POST or a media upload that carries a positive `x-rate-limit-limit`, the account's cap for that endpoint is updated to it, so the limiter follows what x.com currently grants. The pool skips accounts whose limiter denies the endpoint.

**x.com's headers are the authority.** Every response (200 and non-200) that carries both `x-rate-limit-remaining` and `x-rate-limit-reset` updates that account's window for the endpoint. An older response never raises `remaining` inside one window (windows are ordered by their reset timestamp; within a window `remaining` only falls). A response whose `remaining` is at most `RateLimitHeadroom` (2, spare slots for requests already in flight) persists a hold until the reset — that is X's own exhaustion, and nothing client-side releases it early; a real 429 or code 88 marks the endpoint the same way. On top of that the account's budget share gates at read time: the endpoint is held once the window's `remaining` estimate reaches `max(RateLimitHeadroom, limit − max(1, limit*pct/100))` — the complement of the scaled local-counter cap, but never below the in-flight headroom, which applies at every share including the full budget. The budget floor is derived, never persisted — a runtime `SetBudgetPct` that raises the share releases a budget-only hold on the very next pick, while reported exhaustion stands until the reset. In both cases the call that reported the window still succeeds and the next pick rotates to another account, so a 429 that the headers announced never happens. While an endpoint's window is live (before its reset) the local request counter is ignored; the counter decides before the first header is seen (cold start), when responses carry no headers, and again once a window has expired without a renewing response. Writes and media uploads record the window but do not rotate. Observed values are exported as the `twitter.client.ratelimit.*` metrics (see [Metrics](metrics.md)).

**Per-account spend share.** `Account.SetBudgetPct(pct)` restricts the account to `pct` percent of each endpoint's window (1-100; every out-of-range value — 0, negative, above 100 — means 100, the whole window, which is also the never-set default). Both gates enforce the same spend, `max(1, limit*pct/100)` requests per window: the local-counter cap is scaled to it, and under header authority the endpoint is held once `remaining` reaches `limit` minus that spend, floored at `RateLimitHeadroom` at every share. A share of zero cannot be expressed — benching an account entirely is `HoldAccount`'s job. `Account.BudgetPct()` reads it back. It is safe to call at runtime on a live pooled account — the next pick sees the new share, including the release of a budget-only hold.

**Account hold.** `Client.HoldAccount(username, until)` benches a pooled account for every endpoint until the given time — the pool skips it and any waiting call wakes when the hold ends. Re-holding is max-wins: a later call with an earlier `until` never shortens an existing hold; `Client.ReleaseAccount(username)` lifts a hold early. The hold gates only the pool pick — account-pinned writes (`CreateTweet`, `FollowUser`, `UploadMedia`) do not consult it. It is not a failure: no health penalty, no failure counters, no relogin. Returns false when no pool account matches; when every account is held the caller gets the same error a fully-spent pool returns: `pool exhausted for <endpoint> (requires auth): all N items are unavailable`.

**Minimum interval.** `Account.SetMinInterval(d)` allows the pool to pick the account at most once every `d` (for example `3*time.Second` for an account in warm-up); `Account.MinInterval()` reads it back, and `d <= 0` turns it off, which is the default and costs one atomic load per pick. It is safe to call at runtime on a live pooled account — the next pick sees the new value. The pool treats an account inside its interval like any other ineligible one: the call goes to another account at once, so readers see no added delay. When no other account can serve, the call waits until the interval ends — on the same ctx-bounded pool wait as an endpoint limit, within `poolWaitCap` (5 minutes; an interval that would end later fails with the usual `pool exhausted` error). A call already asleep keeps the wake time it computed, so a later `SetMinInterval` takes effect for the next pick, not for that sleep. The interval is measured from pick to pick, and the check and the stamp are one step under the account lock, so concurrent callers cannot both pass. A refused pick spends no rate-limit budget and takes no in-flight slot. Like `HoldAccount` it gates only the pool pick: account-pinned writes (`CreateTweet`, `FollowUser`) and `UploadMedia` do not consult it, and the cap-only retry paths (guest-eligible endpoints, the retry after an endpoint fault) take only an account usable now, so they do not wait for it. It combines with the pacer below by both applying: the interval spaces picks, the pacer then adds its own delay after the pick if the account's previous request was more recent than `AccountPaceMin`. With an interval of a few seconds the pacer adds nothing.

**Request observer.** `ClientConfig.OnRequest func(RequestEvent)`, when set, is called once per HTTP attempt a pooled account served — after the response is classified, on success and on every error path — at the same observation point that feeds `twitter.client.request.duration`. `RequestEvent` carries the username, endpoint, HTTP status, the shared-classifier `Outcome` (the `twitter.outcome` values in [Metrics](metrics.md)), and a `RequestRateLimit` mirroring the response's `x-rate-limit-*` headers (`Limit` 0, `Remaining` -1 and a zero `Reset` mean unknown). Media-upload attempts emit under the `UploadMedia` endpoint label; guest-token fallback attempts carry no account and emit nothing. The hook runs synchronously on the request path and without a recover — it must not block and must not panic.

The `*WithSocial` helpers lease a fresh single-account client per attempt, so that state would die with the lease. They therefore pass the operation to the account service as `?endpoint=<operation>` on acquire and send the last observed window back with the usage report as `rate_limit` (`endpoint`, `limit`, `remaining`, `reset`); see `social.Client.AcquireAccountFor` and `ReportUsageWithRateLimit`. A service that predates these fields ignores them.

On top of that, each account is paced individually on pool requests: a random delay of `AccountPaceMin` to `AccountPaceMin + AccountPaceRandom` (default 0.8s to 2.0s) between consecutive requests by the same account. Pacing is keyed by account, so a busy caller does not delay callers using other accounts. Account-pinned POSTs and media uploads are not paced. Disable pacing with `AccountPaceDisabled`.

Independently of pacing, `MaxInFlightPerAccount` (default 2) bounds how many requests may be in flight on one account at once: the pool skips an account at the cap, and when every eligible account is full the call waits for a slot on the same ctx-bounded machinery as endpoint-limit waits (`pool.wait` metric); the account-pinned paths wait for their own account's slot. A negative value disables the cap. Live in-flight counts are exported as the `twitter.client.pool.inflight` gauge (see [Metrics](metrics.md)). Caveat for `*WithSocial` callers: each lease builds a fresh single-account client, so the cap cannot span concurrent leases of the same underlying account — cross-lease concurrency control belongs to the account service.
