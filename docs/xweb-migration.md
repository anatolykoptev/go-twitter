## Verdicts

- **same-shape**: the response root the go-twitter parser reads is unchanged. Inner tweet/user objects are not diffed.
- **new-shape**: the root moved, or the artifact normalises the timeline through the client's own URT layer (entries arrive as `entry_id` / `content.content` / `details.full_text` / `created_at_ms`, see `xwebTimeline` in `devicefollow.go`), so the legacy timeline parser cannot read it.
- **not-found-in-x-web**: no artifact under any candidate name in the crawled graph.
- **undetermined**: the artifact was found but its response selection could not be read from the chunk.

## Reproducing, and the runtime flag

`go run ./cmd/xweb-report -cache <dir> -out docs/xweb-migration.md -date <YYYY-MM-DD>` re-crawls (the cache keeps re-runs off the network; `-offline` forbids it). The run is a few thousand polite requests for static JavaScript, with four workers and a pause between requests.

The runtime queryId refresher can read the same graph: set `TWITTER_QID_XWEB=on` (default off). It then updates only the operations go-twitter already issues against x-web (currently `tweetNotificationsQuery`); every other operation keeps its legacy id, because an x-web id is a different persisted call (other variables, other response shape).
